### 0.1.2. Умные указатели (Smart Pointers)

### Что такое умные указатели

Умные указатели — это обёртки над обычными указателями (`T*`), которые автоматически управляют временем жизни объекта. Они решают основные проблемы ручного управления памятью: утечки памяти, висячие указатели и двойное удаление.

### Зачем они нужны

**Проблемы с обычными указателями:**
- **Утечки памяти**: легко забыть вызвать `delete`
- **Висячие указатели**: использование удалённого объекта
- **Двойное удаление**: несколько указателей на один объект
- **Неявное владение**: непонятно, кто отвечает за удаление

**Решение умных указателей:**
- Автоматическое удаление объекта при выходе из области видимости
- Явная семантика владения (кто владеет объектом)
- Защита от исключений (RAII-паттерн)
- Меньше ошибок благодаря проверкам на этапе компиляции

### Основные типы умных указателей

#### 1. `std::unique_ptr<T>` — единоличное владение

**Характеристики:**
- Один владелец — объект жив, пока жив этот указатель
- Нельзя копировать (только перемещать через `std::move`)
- Нулевые накладные расходы (как обычный указатель)
- Явное владение: понятно, кто отвечает за удаление

**Когда использовать:**
- Владение объектом у одного владельца
- Передача владения между функциями
- Замена обычных указателей для безопасности

**Пример:**
```cpp
auto obj = std::make_unique<MyClass>();
obj->doSomething();
// Автоматически удалится при выходе из области видимости
```

**Аналогия:** Как ключ от квартиры — только у одного человека, при передаче ключа предыдущий владелец теряет доступ.

#### 2. `std::shared_ptr<T>` — совместное владение

**Характеристики:**
- Несколько владельцев — объект жив, пока есть хотя бы один `shared_ptr`
- Можно копировать (счётчик ссылок увеличивается)
- Есть накладные расходы (счётчик ссылок, atomic операции)
- Безопасно для многопоточности (atomic счётчик)

**Как работает:**
- Внутри есть счётчик ссылок (reference counter)
- При копировании счётчик увеличивается
- При уничтожении указателя счётчик уменьшается
- Когда счётчик = 0, объект удаляется

**Когда использовать:**
- Несколько объектов должны владеть одним ресурсом
- Неясно, кто последний освободит ресурс
- Разделение данных между компонентами

**Пример:**
```cpp
auto shared = std::make_shared<MyClass>();
auto copy1 = shared; // Счётчик: 2
auto copy2 = shared; // Счётчик: 3
// Объект удалится, когда все три указателя будут уничтожены
```

**Аналогия:** Как общий доступ к документу — пока есть читатели, документ существует; когда все закрыли, он удаляется.

#### 3. `std::weak_ptr<T>` — слабая ссылка

**Характеристики:**
- Наблюдение без владения — не увеличивает счётчик ссылок
- Можно проверить, жив ли объект, через `lock()`
- Используется для разрыва циклических ссылок

**Когда использовать:**
- Разрывать циклические ссылки (`shared_ptr` → объект → `shared_ptr`)
- Кэши, которые не должны продлевать жизнь объекта
- Наблюдатели, которые не владеют объектом

**Пример:**
```cpp
std::weak_ptr<MyClass> weak = shared;
if (auto locked = weak.lock()) {
    locked->doSomething(); // Безопасно, если объект ещё жив
}
```

### Когда НЕ нужно использовать умные указатели

#### 1. Не владеющие ссылки (Non-owning references)

Когда указатель используется только для доступа, без владения:

```cpp
void processData(const MyClass* obj) {
    if (obj) {
        obj->doSomething();
    }
    // Функция НЕ удаляет obj, она только использует его
}
```

**Правило:** Если функция не владеет объектом и не продлевает его жизнь, используй `T*` или `const T*`.

#### 2. Критичные к производительности участки

`shared_ptr` добавляет overhead:
- Размер: 16 байт (на 64-bit) вместо 8 байт для `T*`
- Atomic операции для счётчика ссылок
- Дополнительная косвенность (control block)

**Когда это критично:**
- Внутренние циклы рендеринга (60+ FPS)
- Физические расчёты
- Обработка тысяч объектов за кадр

#### 3. Работа с C API и внешними библиотеками

C API не понимает умные указатели. Используй `T*` для интеграции с C библиотеками.

#### 4. Оптимизация размера структуры

`shared_ptr` добавляет overhead (обычно 16+ байт). Для структур данных с миллионами узлов (связные списки, деревья) используй `T*`.

#### 5. Циклические структуры данных

`shared_ptr` создаёт циклические ссылки. Решения:
- Использовать `weak_ptr` (но это overhead)
- Использовать `T*` (если родитель всегда живёт дольше)

#### 6. Временные вычисления и локальные переменные

Когда объект живёт только в пределах функции, используй объект на стеке или явное `new`/`delete`.

#### 7. Низкоуровневые функции выделения памяти

Когда работаешь с сырой памятью без конструкторов/деструкторов, используй `void*` и ручное управление.

### Практическое правило принятия решения

**Задай себе вопросы:**

1. **Владеет ли этот код объектом?** (создаёт/удаляет)
   - Да → `unique_ptr` или `shared_ptr`
   - Нет → `T*` или `const T*`

2. **Вызывается ли это миллионы раз в секунду?**
   - Да → `T*` (производительность)
   - Нет → можно умный указатель

3. **Работаю ли я с C API или сырой памятью?**
   - Да → `T*` или `void*`
   - Нет → можно умный указатель

4. **Нужен ли мне контроль над каждым байтом памяти?**
   - Да → `T*` с ручным управлением
   - Нет → можно умный указатель

### Итоговая рекомендация

**Используй умные указатели по умолчанию**, но переходи на raw указатели, когда:
- Производительность критична
- Объект не владеется (только доступ)
- Работаешь с низкоуровневыми API
- Размер структуры критичен
- Есть специфичное управление памятью (пулы, арены)

**Правило:** Умные указатели для безопасности, raw указатели для производительности и специфичных случаев.

**Главное:** Если функция не владеет объектом, используй `T*` или `const T*`. Это самый частый случай, когда умные указатели не нужны.

### Умные указатели в OpenXRay: xr-версии

В движке OpenXRay используются собственные версии умных указателей, которые интегрированы с системой управления памятью `xrMemory`. Это позволяет всем аллокациям проходить через движковый аллокатор для логирования, профилирования и оптимизации.

**Где в коде:**
- `src/xrCommon/xr_smart_pointers.h` — `xr_unique_ptr`, `xr_shared_ptr`
- `src/xrCore/intrusive_ptr.h` — `intrusive_ptr`

#### 1. `xr_unique_ptr<T>` — единоличное владение через xrMemory

**Что это:**
```cpp
template <typename T>
using xr_unique_ptr = std::unique_ptr<T, xr_custom_deleter<T>>;
```

**Особенности:**
- Это `std::unique_ptr` с кастомным deleter `xr_custom_deleter`
- При удалении объекта используется `xr_delete` вместо обычного `delete`
- Все аллокации проходят через `xrMemory` (логирование, профилирование)
- Поведение идентично `std::unique_ptr`, но интегрировано с движком

**Кастомный deleter:**
```cpp
template <typename T>
struct xr_custom_deleter
{
    void operator()(T* ptr) const noexcept
    {
        xr_delete(ptr);  // Использует движковый аллокатор
    }
};
```

**Создание:**
```cpp
// Используй xr_make_unique вместо std::make_unique
auto obj = xr_make_unique<MyClass>(arg1, arg2);
// Внутри: xr_new<T>(...) → Memory.mem_alloc() → placement new
```

**Пример из кода движка:**
```cpp
// src/xrGame/ai_space.cpp
m_ef_storage = xr_make_unique<CEF_Storage>();
// Объект создаётся через xrMemory и автоматически удалится через xr_delete
```

**Когда использовать:**
- Владение объектом у одного владельца
- Нужна интеграция с системой логирования/профилирования движка
- Все объекты должны проходить через `xrMemory`

---

#### 2. `xr_shared_ptr<T>` — совместное владение через xrMemory

**Что это:**
```cpp
template <typename T>
using xr_shared_ptr = std::shared_ptr<T>;
```

**Особенности:**
- Это обычный `std::shared_ptr`, но с кастомным deleter при создании через `xr_make_shared`
- При создании через `xr_make_shared` используется `xr_new` и `xr_custom_deleter`
- Поведение идентично `std::shared_ptr` (счётчик ссылок, atomic операции)

**Создание:**
```cpp
// Используй xr_make_shared вместо std::make_shared
auto shared = xr_make_shared<MyClass>(arg1, arg2);
// Внутри: xr_new<T>(...) → Memory.mem_alloc() → placement new
//         + xr_custom_deleter для удаления
```

**Реализация:**
```cpp
template <class T, class... Args>
inline xr_shared_ptr<T> xr_make_shared(Args&&... args)
{
    return xr_shared_ptr<T>(xr_new<T>(std::forward<Args>(args)...), 
                           xr_custom_deleter<T>());
}
```

**Когда использовать:**
- Несколько объектов должны владеть одним ресурсом
- Нужна интеграция с `xrMemory`
- Разделение ресурсов между компонентами движка

**Важно:** Если создаёшь `xr_shared_ptr` вручную (не через `xr_make_shared`), убедись, что используешь `xr_custom_deleter`, иначе объект не будет удаляться через `xrMemory`.

#### 3. `intrusive_ptr<T>` — встроенный подсчёт ссылок

**Что это:**
Кастомная реализация умного указателя, где счётчик ссылок хранится **внутри самого объекта**, а не в отдельном control block (как у `shared_ptr`).

**Архитектура:**
```cpp
// Базовый класс для объектов с intrusive_ptr
struct intrusive_base
{
    size_t m_ref_count;  // Счётчик ссылок внутри объекта
    
    void acquire() { ++m_ref_count; }
    bool release() { return --m_ref_count == 0; }
    
    template <typename T>
    void release(T* object) {
        xr_delete(object);  // Удаление через xrMemory
    }
};
```

**Требования к объекту:**
- Объект должен наследоваться от `intrusive_base` (или другого базового класса с методами `acquire()`/`release()`)
- Счётчик ссылок хранится в самом объекте, а не в отдельной структуре

**Как работает:**
```cpp
// При создании intrusive_ptr
intrusive_ptr<MyClass> ptr(new MyClass());
// → вызывает object->acquire() → ++m_ref_count

// При копировании
intrusive_ptr<MyClass> ptr2 = ptr;
// → вызывает object->acquire() → ++m_ref_count (теперь 2)

// При уничтожении
// → вызывает object->release() → --m_ref_count
// → если m_ref_count == 0, вызывает object->release(object) → xr_delete
```

**Реализация:**
```cpp
template <typename ObjectType, typename BaseType = intrusive_base>
class intrusive_ptr
{
    object_type* m_object;
    
    void dec() {
        if (m_object && m_object->release()) {
            m_object->release(m_object);  // Удаление через xrMemory
        }
    }
    
public:
    intrusive_ptr(object_type* rhs) : m_object(rhs) {
        if (m_object) m_object->acquire();
    }
    
    ~intrusive_ptr() { dec(); }
    // ... остальные методы
};
```

**Преимущества перед `shared_ptr`:**
- **Меньше аллокаций**: нет отдельного control block
- **Меньше overhead**: счётчик в объекте, нет дополнительной косвенности
- **Предсказуемый layout**: размер объекта известен заранее
- **Экономия памяти**: особенно важно для объектов, которые часто копируются

**Недостатки:**
- Объект должен быть спроектирован для работы с `intrusive_ptr` (наследование от `intrusive_base`)
- Нельзя использовать с любым типом (как `shared_ptr`)

**Когда использовать:**
- Объекты, которые часто копируются и нужен подсчёт ссылок
- Критична экономия памяти (нет control block)
- Нужен жёсткий контроль над layout объекта
- Объекты уже имеют встроенный счётчик ссылок

**Пример использования:**
```cpp
// Класс должен наследоваться от intrusive_base
class MyResource : public intrusive_base
{
    // ... данные ресурса
};

// Использование
intrusive_ptr<MyResource> resource(new MyResource());
intrusive_ptr<MyResource> copy = resource;  // Счётчик: 2
// При уничтожении всех указателей объект удалится через xr_delete
```

### 0.1.3. Reference counting (ref_sound, ref_light)

**Что это:**
В движке OpenXRay используется собственная система reference counting для ресурсов (звуки, источники света, шейдеры и т.д.). Это похоже на `intrusive_ptr`, но с более специализированной реализацией, оптимизированной для игрового движка.

**Архитектура:**

Система состоит из трёх компонентов:

1. **`xr_resource`** — базовый класс для всех ресурсов с встроенным счётчиком ссылок
2. **`resptr_base<T>`** — базовая обёртка, управляющая счётчиком ссылок
3. **`resptr_core<T, C>`** — финальная обёртка с удобным API

**Базовый класс ресурса:**

```cpp
// src/xrCore/xr_resource.h
struct xr_resource
{
    std::atomic<u32> ref_count{ 0 };  // Атомарный счётчик ссылок
};
```

**Ключевые особенности:**
- Счётчик ссылок хранится **внутри самого объекта** (как у `intrusive_ptr`)
- Счётчик **атомарный** (`std::atomic<u32>`) — безопасен для многопоточности
- Начальное значение: `0` (не `1`, как у `intrusive_ptr`)

**Как работает `resptr_base`:**

```cpp
template <class T>
class resptr_base
{
protected:
    T* p_;  // Указатель на ресурс
    
    void _inc()  // Увеличить счётчик
    {
        if (p_)
            ++p_->ref_count;  // Атомарная операция
    }
    
    void _dec()  // Уменьшить счётчик
    {
        if (p_)
        {
            --p_->ref_count;  // Атомарная операция
            if (0 == p_->ref_count)
                xr_delete(p_);  // Удалить, если счётчик = 0
        }
    }
    
    void _set(T* rhs)  // Установить новый указатель
    {
        if (rhs)
            ++rhs->ref_count;  // Увеличить счётчик нового объекта
        _dec();                // Уменьшить счётчик старого объекта
        p_ = rhs;
    }
};
```

**Как работает `resptr_core`:**

```cpp
template <class T, typename C>
class resptr_core : public C
{
public:
    // Конструктор из указателя
    resptr_core(T* p, bool add_ref = true)
    {
        C::p_ = p;
        if (add_ref)
            C::_inc();  // Увеличить счётчик при создании
    }
    
    // Конструктор копирования
    resptr_core(const self& rhs)
    {
        C::p_ = rhs.p_;
        C::_inc();  // Увеличить счётчик при копировании
    }
    
    // Деструктор
    ~resptr_core()
    {
        C::_dec();  // Уменьшить счётчик при уничтожении
    }
    
    // Оператор присваивания
    self& operator=(const self& rhs)
    {
        this->_set(rhs);  // Правильно обработать старый и новый объекты
        return *this;
    }
    
    // Операторы доступа
    T& operator*() const { return *C::p_; }
    T* operator->() const { return C::p_; }
};
```

**Пример 1: `ref_sound` (звуковой ресурс)**

```cpp
// Определение
struct CSound : public xr_resource
{
    CSound_source* handle;
    // ... другие поля
};

using ref_sound = resptr_core<CSound, resptrcode_sound>;

// Использование
ref_sound sound1;
sound1.create("weapon_shot.ogg", st_Effect, 0);
// После create(): CSound создан, ref_count = 1

ref_sound sound2 = sound1;  // Копирование
// Теперь: ref_count = 2 (оба указателя указывают на один объект)

sound1.destroy();  // Устанавливает sound1.p_ = nullptr
// ref_count уменьшается до 1 (остаётся только sound2)

// Когда sound2 выходит из области видимости:
// ~ref_sound() → _dec() → ref_count = 0 → xr_delete(CSound)
```

**Пример 2: `ref_light` (источник света)**

```cpp
// Определение
class IRender_Light : public xr_resource
{
    // ... виртуальные методы
};

using ref_light = resptr_core<IRender_Light, resptrcode_light>;

// Использование
ref_light torch_light = GEnv.Render->light_create();
// После создания: IRender_Light создан, ref_count = 1

torch_light->set_active(true);
torch_light->set_position(player_pos);
torch_light->set_range(10.0f);

// Если несколько объектов используют один источник света:
ref_light shared_light = torch_light;  // ref_count = 2

// Когда torch_light выходит из области видимости:
// ref_count = 1 (объект всё ещё жив, т.к. shared_light его держит)

// Когда shared_light выходит из области видимости:
// ref_count = 0 → xr_delete(IRender_Light)
```

**Пошаговый разбор жизненного цикла:**

**Шаг 1: Создание ресурса**
```cpp
ref_sound sound;
sound.create("explosion.ogg", st_Effect, 0);
```

Что происходит внутри:
1. `GEnv.Sound->create()` создаёт объект `CSound*` через `xr_new`
2. `_set(CSound*)` вызывается:
   - `++CSound->ref_count` → `ref_count = 1`
   - `p_ = CSound*`
3. Результат: `sound.p_` указывает на `CSound`, `ref_count = 1`

**Шаг 2: Копирование указателя**
```cpp
ref_sound sound_copy = sound;
```

Что происходит:
1. Вызывается конструктор копирования `resptr_core(const self& rhs)`
2. `p_ = rhs.p_` → оба указателя указывают на один `CSound`
3. `_inc()` → `++CSound->ref_count` → `ref_count = 2`
4. Результат: два `ref_sound` указывают на один `CSound`, `ref_count = 2`

**Шаг 3: Изменение указателя**
```cpp
sound.destroy();  // Внутри: _set(nullptr)
```

Что происходит:
1. `_set(nullptr)` вызывается:
   - `rhs = nullptr`, поэтому `++rhs->ref_count` не выполняется
   - `_dec()` вызывается для старого объекта:
     - `--CSound->ref_count` → `ref_count = 1`
     - `ref_count != 0`, поэтому объект НЕ удаляется
   - `p_ = nullptr`
2. Результат: `sound.p_ = nullptr`, `sound_copy` всё ещё держит объект, `ref_count = 1`

**Шаг 4: Уничтожение последнего указателя**
```cpp
// sound_copy выходит из области видимости
```

Что происходит:
1. Вызывается деструктор `~resptr_core()`
2. `_dec()` вызывается:
   - `--CSound->ref_count` → `ref_count = 0`
   - `ref_count == 0`, поэтому вызывается `xr_delete(CSound)`
   - `xr_delete` вызывает деструктор `CSound` и освобождает память через `xrMemory`
3. Результат: объект `CSound` удалён, память освобождена

**Визуализация счётчика ссылок:**

```
Создание:
ref_sound sound1;
sound1.create("shot.ogg", ...);
┌─────────────┐
│   CSound    │
│ ref_count=1 │ ← sound1.p_
└─────────────┘

Копирование:
ref_sound sound2 = sound1;
┌─────────────┐
│   CSound    │
│ ref_count=2 │ ← sound1.p_ и sound2.p_
└─────────────┘

Уничтожение sound1:
sound1.destroy();
┌─────────────┐
│   CSound    │
│ ref_count=1 │ ← только sound2.p_
└─────────────┘
sound1.p_ = nullptr

Уничтожение sound2:
~sound2()
┌─────────────┐
│   CSound    │
│ ref_count=0 │ → xr_delete() → объект удалён
└─────────────┘
```

**Почему атомарный счётчик?**

В многопоточной среде несколько потоков могут одновременно:
- Создавать `ref_sound` из одного ресурса
- Уничтожать `ref_sound`
- Копировать `ref_sound`

Без атомарности возможна **race condition**:
```cpp
// Поток 1:                    Поток 2:
ref_count = 5                 ref_count = 5
ref_count++  // читает 5      ref_count++  // читает 5
ref_count = 6                 ref_count = 6  // ОШИБКА! Должно быть 7
```

С атомарностью операции безопасны:
```cpp
// Поток 1:                    Поток 2:
ref_count = 5                 ref_count = 5
++ref_count  // атомарно      ++ref_count  // атомарно
ref_count = 6                 ref_count = 7  // Правильно!
```

**Отличия от `intrusive_ptr`:**

| Характеристика | `intrusive_ptr` | `resptr_core` (ref_sound/ref_light) |
|----------------|-----------------|-------------------------------------|
| Базовый класс | `intrusive_base` | `xr_resource` |
| Тип счётчика | `size_t` (обычный) | `std::atomic<u32>` (атомарный) |
| Начальное значение | `0` | `0` |
| Увеличение при создании | `acquire()` → `++m_ref_count` | `_inc()` → `++ref_count` |
| Удаление | `release(object)` → `xr_delete` | `_dec()` → `xr_delete` |
| Многопоточность | Небезопасно | Безопасно (atomic) |

**Практические примеры из кода движка:**

**Пример 1: Факел с источником света**
```cpp
// src/xrGame/Torch.h
class CTorch
{
    ref_light light_render;  // Источник света факела
    ref_light light_omni;    // Омни-источник для освещения вокруг
};

// При создании факела:
CTorch::CTorch()
{
    light_render = GEnv.Render->light_create();
    // ref_count = 1 для light_render
    
    light_omni = GEnv.Render->light_create();
    // ref_count = 1 для light_omni
}

// Если факел копируется (например, в инвентаре):
CTorch copy = original;
// light_render копируется → ref_count = 2
// light_omni копируется → ref_count = 2

// Когда оригинальный факел уничтожается:
// ~CTorch() → ~ref_light() → ref_count = 1 (копия всё ещё держит)
```

**Пример 2: Звук выстрела**
```cpp
// src/xrGame/sound_player.cpp
void CSoundPlayer::play(ESoundTypes type, const char* name)
{
    ref_sound sound;
    sound.create(name, st_Effect, type);
    // ref_count = 1
    
    sound.play(player_object);
    // Звук начинает играть, но sound всё ещё держит ресурс
    
    // Когда функция заканчивается:
    // ~ref_sound() → ref_count = 0 → xr_delete(CSound)
    // НО! Если звук всё ещё играет, он может быть сохранён внутри звуковой системы
}
```

**Пример 3: Массив источников света**
```cpp
// src/Layers/xrRender/Light_DB.h
class CLight_DB
{
    xr_vector<ref_light> v_static;  // Статические источники света
    xr_vector<ref_light> v_hemi;    // Полусферические источники
    ref_light sun;                   // Солнце
};

// При загрузке уровня:
void CLight_DB::Load(IReader* fs)
{
    for (int i = 0; i < count; ++i)
    {
        ref_light light = Create();  // ref_count = 1
        v_static.push_back(light);   // Копирование → ref_count = 2
        // light выходит из области видимости → ref_count = 1
        // Объект жив, т.к. v_static[i] его держит
    }
}

// При выгрузке уровня:
void CLight_DB::Unload()
{
    v_static.clear();  // Все ref_light уничтожаются → ref_count = 0 → объекты удаляются
}
```

**Важные моменты:**

1. **Счётчик начинается с 0, а не с 1**
   - При создании `resptr_core(T* p, bool add_ref = true)` счётчик увеличивается
   - Если `add_ref = false`, счётчик остаётся 0 (редкий случай)

2. **Автоматическое удаление при ref_count = 0**
   - Не нужно вручную вызывать `delete`
   - Удаление происходит через `xr_delete` → `xrMemory`

3. **Безопасность при присваивании**
   - `_set()` сначала увеличивает счётчик нового объекта, потом уменьшает старого
   - Это предотвращает удаление объекта, если `new_ptr == old_ptr`

4. **Многопоточная безопасность**
   - `std::atomic<u32>` гарантирует корректную работу в многопоточном коде
   - Операции `++` и `--` атомарны

**Когда использовать `resptr_core` вместо других умных указателей:**

✅ **Используй `resptr_core` (ref_sound, ref_light и т.д.) когда:**
- Работаешь с ресурсами движка (звуки, источники света, шейдеры)
- Нужна многопоточная безопасность
- Объект уже наследуется от `xr_resource`
- Нужна интеграция с системой ресурсов движка

❌ **НЕ используй `resptr_core` когда:**
- Создаёшь свои классы, не наследуемые от `xr_resource`
- Нужен `unique_ptr` (единоличное владение)
- Нужен `shared_ptr` (для совместимости с STL)

**Итог:**

`ref_sound`, `ref_light` и другие `resptr_*` типы — это специализированные умные указатели движка OpenXRay для управления ресурсами с автоматическим подсчётом ссылок. Они похожи на `intrusive_ptr`, но оптимизированы для игрового движка: используют атомарный счётчик для многопоточности и интегрированы с системой управления памятью `xrMemory`.

**Ключевая идея:** Ресурс (звук, свет) живёт, пока на него есть хотя бы одна ссылка (`ref_sound`/`ref_light`). Когда последняя ссылка уничтожается, ресурс автоматически удаляется.

---

### Сравнение типов умных указателей в движке

| Тип | Счётчик ссылок | Аллокации | Overhead | Когда использовать |
|-----|----------------|-----------|----------|-------------------|
| `xr_unique_ptr` | Нет (один владелец) | Одна (объект) | Нет | Единоличное владение |
| `xr_shared_ptr` | В control block | Две (объект + control block) | Да (atomic) | Несколько владельцев |
| `intrusive_ptr` | В объекте | Одна (объект) | Минимальный | Частое копирование, экономия памяти |

### Правила выбора в OpenXRay

1. **По умолчанию**: используй `xr_unique_ptr` для единоличного владения
2. **Несколько владельцев**: используй `xr_shared_ptr` или `intrusive_ptr`
3. **Экономия памяти критична**: выбирай `intrusive_ptr` (если объект поддерживает)
4. **Любой тип**: используй `xr_shared_ptr` (не требует изменений в классе)
5. **Всегда используй `xr_make_unique`/`xr_make_shared`**: для интеграции с `xrMemory`

### Интеграция с xrMemory

Все три типа умных указателей в движке интегрированы с `xrMemory`:
- **Создание**: через `xr_new` → `Memory.mem_alloc()`
- **Удаление**: через `xr_delete` → `Memory.mem_free()`
- **Профит**: логирование, профилирование, оптимизация аллокаций

**Важно:** Всегда используй `xr_make_unique`/`xr_make_shared` вместо `std::make_unique`/`std::make_shared`, чтобы все аллокации проходили через движковый аллокатор.

## 0.2. Контейнеры данных (Data Structures)

### 0.2.1. xr_vector, xr_list, xr_map

**Что это такое и зачем нужно:**

В C++ есть стандартные контейнеры (`std::vector`, `std::list`, `std::map`), которые работают как массивы, списки и словари в JavaScript. Но в игровом движке OpenXRay все эти контейнеры обёрнуты в свои версии (`xr_vector`, `xr_list`, `xr_map`), которые используют движковый аллокатор памяти `xrMemory` вместо стандартного.

**Почему это важно:**

1. **Централизованное управление памятью** — все аллокации проходят через один канал, что позволяет логировать, профилировать и оптимизировать использование памяти
2. **Интеграция с движком** — движок может отслеживать, сколько памяти используется, где происходят утечки, и оптимизировать работу
3. **Единый интерфейс** — все контейнеры работают одинаково, используя одну систему управления памятью

**Аналогия из JavaScript:**

Представь, что в React ты используешь не обычные массивы, а специальные обёртки:
```javascript
// Вместо обычного массива:
const items = [];

// Используешь обёртку, которая логирует все операции:
const items = new TrackedArray(); // Все push/pop логируются
```

В OpenXRay то же самое: вместо `std::vector` используется `xr_vector`, который автоматически использует движковый аллокатор.

---

#### 1. xr_vector — динамический массив

**Что это:**

`xr_vector` — это обёртка над стандартным `std::vector` с использованием движкового аллокатора `xr_allocator`.

**Определение:**
```cpp
// src/xrCommon/xr_vector.h
template <typename T, typename allocator = xr_allocator<T>>
using xr_vector = std::vector<T, allocator>;
```

**Как это работает:**

1. `xr_vector` — это просто `typedef` (алиас) для `std::vector<T, xr_allocator<T>>`
2. Второй параметр шаблона — это аллокатор, который по умолчанию равен `xr_allocator<T>`
3. Когда `std::vector` нужно выделить память, он вызывает `xr_allocator::allocate()`, который в свою очередь вызывает `xrMemory::mem_alloc()`

**Визуализация потока памяти:**

```
xr_vector<int> vec;
vec.push_back(42);

┌─────────────────────────────────────────┐
│ 1. vec.push_back(42)                    │
│    → std::vector нужна память           │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│ 2. std::vector вызывает                │
│    xr_allocator<int>::allocate()        │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│ 3. xr_allocator вызывает               │
│    xr_alloc<int>(n) →                   │
│    Memory.mem_alloc(size)               │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│ 4. Память выделена через xrMemory      │
│    (логирование, профилирование)        │
└─────────────────────────────────────────┘
```

**Простой пример использования:**

```cpp
// Создание вектора целых чисел
xr_vector<int> numbers;

// Добавление элементов (как push в JavaScript)
numbers.push_back(10);  // [10]
numbers.push_back(20);  // [10, 20]
numbers.push_back(30);  // [10, 20, 30]

// Доступ по индексу (как в JavaScript)
int first = numbers[0];   // 10
int second = numbers[1];  // 20

// Размер (как length в JavaScript)
size_t count = numbers.size();  // 3

// Итерация (как for...of в JavaScript)
for (size_t i = 0; i < numbers.size(); ++i) {
    int value = numbers[i];
    // обработка value
}

// Или через итераторы (более C++ стиль)
for (auto it = numbers.begin(); it != numbers.end(); ++it) {
    int value = *it;
    // обработка value
}

// Или range-based for (C++11, самый простой)
for (int value : numbers) {
    // обработка value
}
```

**Пример из реального кода движка:**

```cpp
// src/xrEngine/xr_object_list.h
class CObjectList
{
private:
    typedef xr_vector<IGameObject*> Objects;
    Objects destroy_queue;      // Очередь объектов на удаление
    Objects objects_active;     // Активные объекты
    Objects objects_sleeping;   // Спящие объекты
};
```

**Характеристики `xr_vector`:**

- **Хранение:** элементы хранятся в непрерывном блоке памяти (как обычный массив)
- **Доступ:** O(1) по индексу (мгновенный доступ к любому элементу)
- **Вставка в конец:** O(1) амортизированно (быстро, но иногда нужно перевыделить память)
- **Вставка в начало/середину:** O(n) (медленно, нужно сдвигать элементы)
- **Удаление:** O(n) для начала/середины, O(1) для конца
- **Память:** элементы хранятся компактно, хорошая локальность данных (cache-friendly)

**Когда использовать:**

✅ **Используй `xr_vector`, когда:**
- Нужен быстрый доступ по индексу
- Часто добавляешь элементы в конец
- Элементы хранятся последовательно
- Нужна компактность памяти

❌ **НЕ используй `xr_vector`, когда:**
- Часто вставляешь/удаляешь элементы в начале или середине
- Нужна стабильность указателей (указатели на элементы могут инвалидироваться при изменении размера)

#### 2. xr_list — двусвязный список

**Что это:**

`xr_list` — это обёртка над стандартным `std::list` (двусвязный список) с использованием движкового аллокатора.

**Определение:**
```cpp
// src/xrCommon/xr_list.h
template <typename T, typename allocator = xr_allocator<T>>
using xr_list = std::list<T, allocator>;
```

**Как это работает:**

`std::list` — это двусвязный список, где каждый элемент хранит указатели на предыдущий и следующий элементы. Элементы не хранятся в непрерывной памяти, а разбросаны по куче.

**Визуализация структуры:**

```
xr_list<int> list;
list.push_back(10);
list.push_back(20);
list.push_back(30);

В памяти это выглядит так:

┌─────────┐    ┌─────────┐    ┌─────────┐
│ prev: 0 │    │ prev:─┐ │    │ prev:─┐ │
│ data:10 │◄───┤ data:20│◄───┤ data:30│
│ next:──┼┼───►│ next:──┼┼───►│ next: 0 │
└─────────┘    └─────────┘    └─────────┘
   элемент 1      элемент 2      элемент 3
```

**Простой пример использования:**

```cpp
// Создание списка
xr_list<int> numbers;

// Добавление элементов
numbers.push_back(10);   // [10]
numbers.push_back(20);   // [10, 20]
numbers.push_front(5);   // [5, 10, 20] - добавление в начало

// НЕТ доступа по индексу! (в отличие от vector)
// numbers[0] - ОШИБКА! Так нельзя

// Только через итераторы
auto it = numbers.begin();
int first = *it;  // 5
++it;
int second = *it; // 10

// Или range-based for
for (int value : numbers) {
    // обработка value
}

// Вставка в середину (быстро!)
auto middle = numbers.begin();
++middle;  // указывает на 10
numbers.insert(middle, 15);  // [5, 15, 10, 20]

// Удаление элемента
numbers.erase(middle);  // удаляет 10, получается [5, 15, 20]
```

**Характеристики `xr_list`:**

- **Хранение:** элементы хранятся в отдельных узлах, связанных указателями
- **Доступ:** O(n) по позиции (нужно пройти от начала до нужного элемента)
- **Вставка:** O(1) в любом месте (если есть итератор)
- **Удаление:** O(1) из любого места (если есть итератор)
- **Память:** больше overhead (каждый элемент хранит 2 указателя), плохая локальность данных

**Когда использовать:**

✅ **Используй `xr_list`, когда:**
- Часто вставляешь/удаляешь элементы в середине
- Нужна стабильность итераторов (итераторы не инвалидируются при вставке/удалении)
- Не нужен доступ по индексу

❌ **НЕ используй `xr_list`, когда:**
- Нужен быстрый доступ по индексу
- Важна компактность памяти
- Часто итерируешься по всем элементам (плохая cache locality)

**Сравнение с JavaScript:**

В JavaScript нет прямого аналога связного списка, но можно представить как:
```javascript
// В JavaScript массивы могут работать как vector или list
// Но в C++ это разные структуры с разными характеристиками

// xr_vector ≈ JavaScript Array (но с фиксированным поведением)
const arr = [1, 2, 3];
arr.push(4);  // быстро
arr.unshift(0);  // медленно (сдвигает все элементы)

// xr_list ≈ гипотетический LinkedList (если бы был)
// Вставка в середину всегда быстрая, но нет доступа по индексу
```

#### 3. xr_map — ассоциативный массив (словарь)

**Что это:**

`xr_map` — это обёртка над стандартным `std::map` (красно-чёрное дерево) с использованием движкового аллокатора. Это ассоциативный контейнер, который хранит пары ключ-значение в отсортированном порядке.

**Определение:**
```cpp
// src/xrCommon/xr_map.h
template <typename K, class V, class P = std::less<K>, 
          typename allocator = xr_allocator<std::pair<const K, V>>>
using xr_map = std::map<K, V, P, allocator>;
```

**Параметры шаблона:**
- `K` — тип ключа (например, `int`, `string`)
- `V` — тип значения (например, `IGameObject*`)
- `P` — функция сравнения (по умолчанию `std::less<K>` — сортировка по возрастанию)
- `allocator` — аллокатор (по умолчанию `xr_allocator`)

**Как это работает:**

`std::map` реализован как красно-чёрное дерево — самобалансирующееся бинарное дерево поиска. Элементы автоматически сортируются по ключу.

**Визуализация структуры:**

```
xr_map<string, int> scores;
scores["Alice"] = 100;
scores["Bob"] = 85;
scores["Charlie"] = 95;

В памяти это красно-чёрное дерево:

        "Bob" (85)
       /        \
"Alice" (100)  "Charlie" (95)
```

**Простой пример использования:**

```cpp
// Создание map (словаря)
xr_map<string, int> scores;

// Вставка элементов (как в JavaScript объект)
scores["Alice"] = 100;
scores["Bob"] = 85;
scores["Charlie"] = 95;

// Доступ к элементам
int aliceScore = scores["Alice"];  // 100

// Проверка существования (важно! оператор [] создаёт элемент, если его нет)
if (scores.find("David") != scores.end()) {
    // ключ существует
    int davidScore = scores["David"];
}

// Или через at() (бросает исключение, если ключа нет)
try {
    int davidScore = scores.at("David");
} catch (const std::out_of_range& e) {
    // ключ не найден
}

// Итерация (элементы идут в отсортированном порядке!)
for (auto& pair : scores) {
    string name = pair.first;   // ключ
    int score = pair.second;    // значение
    // "Alice" (100), "Bob" (85), "Charlie" (95)
}

// Удаление
scores.erase("Bob");  // удаляет пару с ключом "Bob"
```

**Пример из реального кода движка:**

```cpp
// src/xrGame/xrServer.h
using xrS_entities = xr_map<u16, CSE_Abstract*>;
// Карта: ID объекта → указатель на объект

xrS_entities entities;

// Добавление объекта
entities[object_id] = object_ptr;

// Поиск объекта по ID
auto it = entities.find(object_id);
if (it != entities.end()) {
    CSE_Abstract* obj = it->second;  // найденный объект
}
```

**Характеристики `xr_map`:**

- **Хранение:** элементы хранятся в виде красно-чёрного дерева
- **Поиск:** O(log n) — логарифмическое время
- **Вставка:** O(log n) — логарифмическое время
- **Удаление:** O(log n) — логарифмическое время
- **Порядок:** элементы всегда отсортированы по ключу
- **Память:** больше overhead, чем у `xr_vector` (каждый узел хранит указатели)

**Когда использовать:**

✅ **Используй `xr_map`, когда:**
- Нужен быстрый поиск по ключу
- Нужна сортировка по ключу
- Ключи уникальны (один ключ → одно значение)
- Нужна предсказуемая производительность

❌ **НЕ используй `xr_map`, когда:**
- Нужна максимальная скорость (используй `xr_unordered_map` — хеш-таблицу)
- Ключи — это просто индексы 0, 1, 2... (используй `xr_vector`)
- Нужна компактность памяти

**Сравнение с JavaScript:**

```javascript
// В JavaScript объекты и Map работают похоже
const scores = {};
scores["Alice"] = 100;
scores["Bob"] = 85;

// Но в C++ xr_map:
// 1. Всегда отсортирован по ключу
// 2. Гарантированная O(log n) производительность
// 3. Строгая типизация (ключ и значение имеют фиксированные типы)
```

#### Как работает аллокатор (xr_allocator)

**Что такое аллокатор:**

Аллокатор — это объект, который управляет выделением и освобождением памяти для контейнеров. Вместо того чтобы контейнеры напрямую вызывали `malloc`/`new`, они используют аллокатор, который можно подменить.

**Определение `xr_allocator`:**

```cpp
// src/xrCommon/xr_allocator.h
template <typename T>
using xr_allocator = xalloc<T>;
```

**Реализация `xalloc`:**

```cpp
// src/xrCore/Memory/xalloc.h
template <typename T>
class xalloc
{
public:
    // Выделение памяти для n элементов типа T
    static pointer allocate(const size_type n, const void* p = nullptr) 
    { 
        return xr_alloc<T>(n);  // Вызывает xrMemory
    }
    
    // Освобождение памяти
    static void deallocate(pointer p, const size_type /*n*/) 
    { 
        xr_free(p);  // Вызывает xrMemory
    }
};
```

**Поток вызовов при выделении памяти:**

```
xr_vector<int> vec;
vec.push_back(42);

1. std::vector::push_back() нужна память
   ↓
2. Вызывает xr_allocator<int>::allocate(n)
   ↓
3. xr_allocator вызывает xr_alloc<int>(n)
   ↓
4. xr_alloc вызывает Memory.mem_alloc(size)
   ↓
5. xrMemory выделяет память через mimalloc/malloc
   ↓
6. Память выделена, std::vector использует её
```

**Зачем это нужно:**

1. **Логирование** — можно отслеживать все аллокации
2. **Профилирование** — можно измерять использование памяти
3. **Оптимизация** — можно использовать пулы памяти, арены и другие техники
4. **Отладка** — можно находить утечки памяти
5. **Единообразие** — все контейнеры используют одну систему

**Простая аналогия:**

Представь, что вместо того чтобы каждый раз идти в банк за деньгами, ты используешь единый финансовый менеджер:

```javascript
// Вместо прямого обращения к банку:
const money = bank.withdraw(1000);  // каждый раз идёшь в банк

// Используешь менеджера, который:
const money = financeManager.withdraw(1000);
// - логирует все операции
// - отслеживает баланс
// - оптимизирует запросы
// - может использовать кэш
```

В OpenXRay `xr_allocator` — это такой "финансовый менеджер" для памяти.

#### Сравнительная таблица контейнеров

| Характеристика | `xr_vector` | `xr_list` | `xr_map` |
|----------------|-------------|-----------|----------|
| **Структура** | Динамический массив | Двусвязный список | Красно-чёрное дерево |
| **Доступ по индексу** | O(1) ✅ | ❌ Нет | ❌ Нет |
| **Поиск по ключу** | O(n) ❌ | O(n) ❌ | O(log n) ✅ |
| **Вставка в конец** | O(1) ✅ | O(1) ✅ | - |
| **Вставка в начало** | O(n) ❌ | O(1) ✅ | - |
| **Вставка в середину** | O(n) ❌ | O(1) ✅ | O(log n) |
| **Удаление** | O(n) | O(1) | O(log n) |
| **Память** | Компактная ✅ | Overhead (указатели) | Overhead (дерево) |
| **Cache locality** | Отличная ✅ | Плохая ❌ | Средняя |
| **Сортировка** | Нет (можно отсортировать) | Нет | Автоматическая ✅ |
| **Стабильность итераторов** | ❌ Инвалидируются | ✅ Стабильны | ✅ Стабильны |

#### Практические рекомендации

**Когда что использовать:**

1. **`xr_vector`** — используй по умолчанию для большинства случаев:
   - Списки игровых объектов
   - Массивы координат, вершин
   - Буферы данных
   - Когда нужен быстрый доступ по индексу

2. **`xr_list`** — используй редко, только когда:
   - Часто вставляешь/удаляешь в середине
   - Нужна стабильность итераторов
   - Не нужен доступ по индексу

3. **`xr_map`** — используй когда:
   - Нужен поиск по ключу
   - Нужна сортировка
   - Ключи не являются последовательными индексами

**Правило большого пальца:**

> **90% случаев используй `xr_vector`**. Переходи на `xr_map` только когда нужен поиск по ключу, и на `xr_list` только когда критична вставка в середину.

---

#### Итог

`xr_vector`, `xr_list` и `xr_map` — это обёртки над стандартными контейнерами C++, которые используют движковый аллокатор `xrMemory` вместо стандартного. Это позволяет:

- Централизованно управлять памятью
- Логировать и профилировать аллокации
- Интегрироваться с системой движка

**Ключевая идея:** Все три контейнера работают так же, как их стандартные аналоги (`std::vector`, `std::list`, `std::map`), но все операции с памятью проходят через `xrMemory`, что даёт движку контроль над управлением памятью.
